# PRISM-AI — полный план разработки

PRISM-AI (Predictive Recruitment Intelligence & Success Modeling) — самостоятельная recruiting CRM/ATS для ведения вакансий, базы кандидатов и резюме, контактов и задач по кандидатам, этапов отбора, прогнозов и аналитики. Приложение имеет собственную локальную базу, пользовательский интерфейс и API; оно работает независимо от сторонних HRM/ATS-платформ. На macOS собирается автономный `.app`, DMG создаётся при необходимости переноса; Cloudflare и hh.ru подключаются как внешние сервисы по своим функциям, а экспорт в HRMS остаётся дополнительной интеграцией. Прогнозы помогают специалисту анализировать информацию, но не принимают решение о найме вместо него.

Это последовательная инструкция по созданию полного продукта, а не сокращённой версии. Все пункты являются работами к выполнению, а контрольные точки закрываются указанными критериями и коммитами. Технические решения уже заданы в документе: macOS-приложение на Tauri/React, локальный Python API, собственный синтетический сквозной датасет, обученная многоцелевая нейросеть и Cloudflare Workers AI через AI Gateway для текстового объяснения результата.

## 0. Принципы проекта и решения, которые нельзя терять

### 0.1. Продуктовая граница

- [ ] Реализовать целиком рабочее приложение: вакансии, кандидаты, загрузка и разбор резюме, этапы отбора, прогнозы, аналитика, рыночные вакансии, локальное хранение, резервное копирование, экспорт и macOS-сборка.
- [ ] Реализовать продукт как самостоятельную рекрутинговую CRM/ATS: собственные сущности, база кандидатов и вакансий, история коммуникаций и действий, воронка заявок, аналитика и настройки. PRISM-AI является источником истины для всех основных рабочих данных и не требует внешней HRMS для запуска.
- [ ] Сохранить участие рекрутера на каждом решающем шаге. Не вводить автоматическое отклонение, рейтинг «годен/не годен» или скрытый порог, который сам меняет статус кандидата.
- [ ] Разделить два назначения: (а) сопоставление компетенций с конкретной вакансией; (б) исследовательский прогноз будущих результатов найма. Высокое совпадение резюме с вакансией само по себе не доказывает будущую успешность работника.
- [ ] Отображать отдельно исходные факты, оценки специалиста и результаты модели; сохранять происхождение каждого значения, включая открытый источник, параметр генератора и версию синтетического набора.
- [ ] Показывать метрики на том наборе, на котором они рассчитаны. Сквозную модель обучать и тестировать на собственном синтетическом датасете, приближенном к описанным профилям реальных процессов; в отчётах указывать, что именно измеряется в этом учебном эксперименте.
- [ ] Не использовать имя ООО «Термоцентр», товарные знаки и фирменное оформление компании в продукте, seed-данных или интерфейсе. Использовать нейтральные формулировки «Компания», «организация», «работодатель».

### 0.2. Политика в отношении данных и моделей

- [ ] Обучать сквозную многоцелевую нейросеть на собственной синтетической выборке; обучать отдельные benchmark-модели на открытых датасетах по тем меткам и задачам, которые в них представлены.
- [ ] Использовать распределения, связи и метки открытых наборов для профилирования и калибровки генератора, сохраняя смысл каждой метки. Синтетическая сквозная выборка объединяет совместимые закономерности нескольких источников через вероятностную модель, а не через фиктивное объединение записей людей.
- [ ] Во всех наборах и артефактах хранить `data_origin`, `label_origin`, URL/идентификатор источника, версию, дату получения, лицензию/условия, seed генерации и версию конфигурации.
- [ ] Для учебной разработки использовать открытые и синтетические данные; реальные кадровые данные организации не требуются ни для обучения, ни для тестирования проекта.
- [ ] Вести `model_card` для каждой модели: предназначение, версия данных, состав признаков, метрики, ограничения, группы риска, дата обучения и допустимый сценарий использования.

## 1. Подготовка репозитория и спецификация продукта

Не устанавливать зависимости проекта в глобальный Python, Node или Rust.
- [ ] Использовать Python 3.12+ для локального API и ML-слоя: FastAPI, Pydantic, SQLAlchemy 2, Alembic; создать `pyproject.toml` и lock-файл окружения, проверять совместимость на целевой версии macOS.

- [ ] Создать `scripts/setup_dev.sh`, который из корня репозитория проверяет системные prerequisites, создаёт `.venv`, устанавливает зафиксированные Python/Node/Rust зависимости и необходимые Tauri/macOS компоненты, затем проверяет их версии. Создать `scripts/check_env.sh` для диагностики окружения.

- [ ] Для локальной базы использовать SQLite в каталоге приложения пользователя, включить миграции и резервное копирование. Не хранить базу внутри `.app` или каталога исходников.
- [ ] Выполнять разбор пачки резюме, импорт, аналитические пересчёты и inference в background worker; показывать состояние, прогресс, отмену и ошибки.
- [ ] Поддерживать macOS 13+ на Apple Silicon (arm64); собирать локальное приложение `dist/PRISM-AI.app`. Создавать DMG только как удобный контейнер для переноса этой сборки на тот же Mac; не готовить коммерческую дистрибуцию.

## 2. Предметная модель, потоки и контракт продукта

### 2.1. Описать полный путь данных

- [ ] Зафиксировать процесс: вакансия → поступление резюме → извлечение сведений → проверка специалистом → сопоставление с требованиями → первичный просмотр → тестирование → собеседование → решение → предложение/выход → испытательный срок/адаптация → результаты работы и наблюдение удержания.
- [ ] Для каждого этапа указать, какие поля появляются, кто их вводит, когда они становятся доступны модели и какие поля являются результатом после найма.
- [ ] Разделить состояния кандидата (`new`, `screening`, `assessment`, `interview`, `offer`, `hired`, `rejected`, `withdrawn`, `archived`) и историю переходов. Не затирать историю при перемещении кандидата.
- [ ] Поддержать несколько откликов одного человека на разные вакансии: сущность `Candidate` отдельно от `Application`; признаки соответствия и прогнозы привязать к заявке, а не только к человеку.
- [ ] Сохранить версии вакансии и критериев: изменение требований не должно переписывать, по каким критериям оценивалась прежняя заявка.

### 2.2. Спроектировать сущности и связи

- [ ] `CompanyProfile`: нейтральное имя, настройки, часовой пояс, валюты, справочники.
- [ ] `Vacancy`: название, подразделение, локация/формат, описание, уровень, диапазон оплаты, обязательные и желательные навыки, требования к опыту/образованию, даты и статус.
- [ ] `Candidate`: локальный ID, контактные данные (только необходимые), источник, согласие/основание обработки, статус удаления/архивации.
- [ ] `ResumeDocument`: безопасная ссылка на файл, тип, хэш, дата импорта, извлечённый текст, язык, версия парсера, статус проверки человеком; оригинал и извлечённый текст удаляются по правилам хранения.
- [ ] `Application`: связь кандидата с вакансией, дата отклика, статус, этап, источник и версия описания вакансии.
- [ ] `CandidateSkill`, `Experience`, `Education`, `Certification`, `Assessment`, `Interview`, `StageEvent`: нормализованные записи, оценка, комментарий и автор оценки.
- [ ] `CandidateInteraction` и `RecruiterTask`: контакт/событие по кандидату (дата, канал, тип, краткий результат, ответственный) и задача рекрутера (срок, статус, приоритет, связь с кандидатом/вакансией); показать открытые задачи и историю действий в карточках.
- [ ] `Outcome`: дата выхода, испытательный срок, производительность с определённым периодом и источником измерения, адаптация, время до целевой производительности, дата увольнения/цензурирования наблюдения.
- [ ] `HiringCost`: компоненты затрат, валюта, правило пересчёта, период и источник; `VacancyTiming`: даты открытия, первого выхода, закрытия и определение метрики.
- [ ] `Prediction`: модель и версия, момент прогноза, допустимые на этот момент входы, выходы, доверительная оценка, объяснение, версия данных и отметка, что человек принял/изменил решение.
- [ ] `AuditEvent`, `ImportJob`, `MarketSnapshot`, `ModelArtifact`, `MetricSnapshot`: аудит, фоновые задачи, снимки рынка и метаданные аналитики/моделей.
- [ ] Задать ограничения целостности, внешние ключи, индексы, уникальность идентификаторов импорта и правила удаления/анонимизации.

### 2.3. Описать API-контракт

- [ ] Описать OpenAPI эндпоинты для вакансий, кандидатов, заявок, документов, этапов, оценок, прогнозов, аналитики, импорта/экспорта, снимков рынка, настроек и статуса фоновых задач.
- [ ] Ввести схемы входа/выхода с версиями, пагинацией, фильтрами, сортировкой, единым форматом ошибок и проверкой размеров загрузок.
- [ ] Для обновлений использовать идемпотентность там, где возможен повтор запроса; долгие задачи возвращают ID задания, состояние и результат.
- [ ] Добавить проверку готовности локального API и версию совместимости frontend/API/model schema.
- [ ] Генерировать TS-контракты из OpenAPI или поддерживать общие схемы без ручного расхождения типов.

**Критерий контрольной точки:** схема сущностей и OpenAPI покрывают все сценарии от создания вакансии до аналитики состоявшегося найма, миграции создают рабочую пустую базу.

## 3. Источники, датасеты и права использования

### 3.1. Реестр открытых источников

Для каждого источника создать запись в `data/sources/registry.yml`: точное имя, URL, дата проверки, владелец/автор, лицензия или условия, язык, типичный размер, поля, способ получения, происхождение меток, синтетический ли набор, назначение и запреты.

- [ ] **AI Recruitment Pipeline Dataset (Kaggle)** — https://www.kaggle.com/datasets/yaswanthkumary/ai-recruitment-pipeline-dataset/data. Профилировать поля и переходы этапов, обучить отдельную модель для представленной в датасете метки и использовать частоты этапов в генераторе. Не переименовывать decision label в performance/retention: в синтетическом датасете эти постнаймовые цели генерируются отдельно.
- [ ] **Resume Data for Ranking (Kaggle)** — https://www.kaggle.com/datasets/thejohnwick001/resume-data-for-ranking. Профилировать текст, вакансии, ranking/score и способ разметки; обучить отдельный ranking benchmark на его train split, использовать совместимые характеристики текста и релевантности при построении собственного корпуса.
- [ ] **AI Fair Recruitment Dataset (Kaggle)** — https://www.kaggle.com/datasets/roiiith/ai-fair-recrutment-dataset. Профилировать признаки, метки и чувствительные атрибуты; обучить отдельную модель на целевой метке набора и использовать его для проверки влияния смещения. Его hiring label сохраняет исходный смысл и не переименовывается в качество работы после найма.
- [ ] **HR Analytics / Employee Dataset** — https://www.kaggle.com/datasets/ravindrasinghrana/employeedataset. Разобрать каждую таблицу отдельно; модели по `performance`, `attrition`, satisfaction/training строить только на фактически присутствующих полях и документировать их семантику. Не связывать таблицы с резюме фиктивными ID.
- [ ] **Employees Attrition and Leadership Impact HR Data** — https://www.kaggle.com/datasets/shree317/employees-attrition-and-leadership-impact-hr-data. Разобрать распределения hiring cost, duration, performance и retention в отдельных профилях; значения использовать как маргинальные/условные калибровки для учебной генерации только при наличии соответствующих колонок.
- [ ] **Resume Screening Dataset — 200K Candidates** — https://www.kaggle.com/datasets/rhythmghai/resume-screening-dataset-200k-candidates. Использовать как открытый синтетический источник для проверки парсинга и больших объёмов, обучения модели по его собственным меткам, а также профилирования текста и атрибутов резюме.

### 5.3. Объём и метод генерации

- [ ] Сформировать основную синтетическую выборку **150 000 заявок**; создать 30 000 синтетических вакансий и не менее 75 000 синтетических кандидатов, чтобы одни кандидаты могли откликаться на несколько вакансий. 150 000 — фиксированный экспериментальный размер в целевом плане.
- [ ] До генерации заявок распределить все candidate IDs и vacancy IDs по `train/validation/test = 70/15/15` с seed `20261030`; генерировать каждую заявку только внутри одного split и не допускать повторных candidate/vacancy IDs между splits.
- [ ] Реализовать гибридный генератор: фиксированный DAG процесса задаёт порядок причинных/условных зависимостей, а условные распределения и частоты семплируются из очищенных профилей исходных наборов. Открытые наборы не объединять по идентификаторам и не выдавать за одну реальную когорту.
- [ ] Для каждой переменной рассчитывать параметры условных распределений по исходным данным, когда соответствующие колонки и их определения совпадают. При малой ячейке применять backoff по иерархии `роль+уровень → семейство ролей → общий профиль`; записывать effective sample size и уровень backoff.
- [ ] Использовать сглаживание категориальных вероятностей Лапласа: $\hat p_k=(n_k+\alpha)/(N+K\alpha)$ при $\alpha=1$, чтобы редкая/неувиденная категория не получала нулевую вероятность.

## 6. Формулы и целевые переменные

### 6.1. Сопоставление кандидата с вакансией

Для вакансии $v$ задаются веса требований $w_j\ge0$, причём $\sum_j w_j=1$, и подтверждённое соответствие $m_j\in\{0,0.5,1\}$ (нет, частично, подтверждено). Покрытие навыков:

\[
S_{skill}(c,v)=\frac{\sum_{j=1}^{J} w_jm_j}{\sum_{j=1}^{J}w_j},\qquad
S_{text}(c,v)=\frac{1+\cos(\mathbf e_c,\mathbf e_v)}{2}.
\]

Текстовое сходство отображаем отдельно и не считаем доказательством компетенции. Индекс сопоставления:

\[
M(c,v)=\alpha_sS_{skill}+\alpha_eS_{experience}+\alpha_qS_{qualification}+\alpha_tS_{text},\quad \sum\alpha=1.
\]

- [ ] Для начальной настраиваемой конфигурации использовать $(\alpha_s,\alpha_e,\alpha_q,\alpha_t)=(0.50,0.20,0.15,0.15)$; это прозрачное инженерное стартовое значение, не научно установленная истина. Хранить конфигурацию и версию, проводить чувствительный анализ и дать специалисту менять её.
- [ ] Если у вакансии нет заданных навыков/критериев, возвращать `S_skill=null` и просить заполнить профиль вместо деления на ноль; иначе показывать обязательные критерии отдельно как статусы `подтверждено / не подтверждено / нужно проверить`. Не позволять высокому текстовому сходству скрывать отсутствие обязательного допуска/навыка.
- [ ] Опыт и образование считать только по конкретным требованиям вакансии и заданным правилам эквивалентности; не использовать один общий «идеальный» профиль на все роли.
- [ ] В интерфейсе объяснять, какие факты подтверждают навык, какие сомнительны и какие требуют ручной проверки.

### 6.2. Качество состоявшегося найма

Пусть для найма $i$: $P_i\in[0,1]$ — результативность в окне 90–180 дней после выхода, $R_{i,12}\in\{0,1\}$ — факт работы на 365-й день после выхода, $A_i\in[0,1]$ — успешность адаптации/испытательного срока, $V_i\in[0,1]$ — скорость выхода на установленный для данной роли уровень производительности.

В синтетическом наборе хранить два целевых представления. `potential_Q` и его компоненты генерируются для всех заявок по заданной модели процесса и являются основными supervised targets для обучения и тестирования stage-моделей. Это заданная генератором учебная ground truth, приближённая к профилям открытых HR-наборов. `observed_Q` моделирует измеренный результат для hired-сотрудников с завершённым окном наблюдения; для rejected и незрелых наблюдений поля остаются `null`. Отчёт указывает версию генератора и показывает, насколько модель восстановила закономерности созданного учебного процесса.

Для оценки «чем выше, тем лучше» нормировать утверждённый KPI по границам роли, заданным до анализа данных: $P_i=\operatorname{clip}((KPI_i-P_{min,r})/(P_{max,r}-P_{min,r}),0,1)$. Если KPI имеет обратное направление, инвертировать шкалу. Удержание: $R_{i,12}=1$, если сотрудник наблюдался работающим в заранее определённой точке 365 дней после выхода, и $0$, если он ушёл раньше; если 365-дневное окно ещё не наблюдалось, метка неизвестна, а не равна нулю. Адаптацию задавать утверждённой шкалой: бинарно (испытательный срок пройден/не пройден) либо по рубрике, нормированной к $[0,1]$. Пусть $d_i$ — число дней до достижения заранее определённого уровня производительности; тогда $V_i=1-\operatorname{clip}((d_i-d_{min,r})/(d_{max,r}-d_{min,r}),0,1)$. Границы $P_{min,r},P_{max,r},d_{min,r},d_{max,r}$ задаются по роли до моделирования, а не вычисляются из полной выборки.

\[
Q_i=w_PP_i+w_RR_{i,12}+w_AA_i+w_VV_i,
\qquad w_k\ge0,\quad w_P+w_R+w_A+w_V=1.
\]

- [ ] Использовать в `quality_labels_v1.yml` фиксированные окна: KPI — оценка за дни 90–180, удержание — employment status на день 365, адаптация — прохождение испытательного срока, ramp-up — дни от выхода до достижения целевого KPI. Для сотрудников без полного окна соответствующая метка остаётся null; увольнение до 365 дней даёт `R12=0`.
- [ ] Зафиксировать границы нормирования KPI и скорости достижения производительности в versioned-конфигурации по семейству ролей; при неизвестных границах или отсутствии KPI компонент оставить неизвестным, не подставлять ноль.
- [ ] Не считать отсутствие исхода отрицательным исходом. Для ранней версии целевого расчёта включать только случаи с полностью наблюдаемым окном; для правого цензурирования отдельно исследовать survival-модель, например удержание и время до ухода.
- [ ] Использовать в основном синтетическом датасете фиксированные веса `quality_weights_v1 = {performance: 0.40, retention_12m: 0.30, adaptation: 0.20, ramp_up_speed: 0.10}`. Они дают приоритет результативности и удержанию, как предполагает ВКР; в UI показать эту формулу и версию. Для `observed_Q` использовать только строки, где наблюдаются все четыре компонента; иначе `observed_Q=null`, не перенормировать веса молча.
- [ ] Обучить дополнительные исследовательские конфигурации весов `{0.25,0.25,0.25,0.25}`, `{0.50,0.25,0.15,0.10}` и `{0.30,0.40,0.20,0.10}`; пересчитать ранжирование/метрики и включить анализ чувствительности в результат эксперимента. В штатной модели использовать только `quality_weights_v1`.
- [ ] Не рассчитывать $P_i$ по шкале, оценённой после просмотра прогноза; использовать утверждённые KPI/оценки с периодом и источником.
- [ ] Для соответствующих моделей предсказывать компоненты $(P,R,A,V)$ отдельно и агрегат $Q$. Бинарные/временные/непрерывные задачи оценивать своими метриками.

### 6.3. Эффективность найма

Затраты $C_i$ и время $T_i$ сравниваются с медианами $C_{ref,g},T_{ref,g}$ для группы по семейству должностей и уровню за предшествующие 12 месяцев. Минимальный размер группы — 30 закрытых вакансий; при меньшей группе использовать сначала медиану семейства должностей, затем общую медиану. Все baseline рассчитывать только на обучающем/историческом периоде. Безразмерный индекс:

\[
E_i^{raw}=Q_i\times\left(\frac{C_{ref,g}}{\max(C_i,\epsilon)}\right)^{\beta_C}
\times\left(\frac{T_{ref,g}}{\max(T_i,\epsilon)}\right)^{\beta_T},\qquad
E_i=\frac{E_i^{raw}}{1+E_i^{raw}}.
\]

- [ ] В формуле использовать $\epsilon_C=1$ единица валюты и $\epsilon_T=1$ день; хранить валюту затрат, пересчитывать разные валюты в RUB по официальному курсу даты снимка и сохранять дату/значение курса.
- [ ] Использовать начальные веса $\beta_C=0.5,\beta_T=0.5$ только как baseline; показывать рядом $(Q,C,T)$ и базовые значения, чтобы единый балл не скрывал компромисс.
- [ ] Рассчитывать базовые значения по предшествующему периоду/сопоставимой группе, а не по всей выборке, содержащей будущие значения теста. При малой группе использовать заданный fallback уровня выше и явно помечать его.
- [ ] Отделять показатель результата найма (Q) от затрат и длительности процесса. Изменения (C,T) не являются доказанным причинным эффектом ML без контролируемого сравнения.
- [ ] Не применять обычный min-max, рассчитанный на полном датасете: он протекает в test и меняет шкалу при каждом новом наблюдении.

### 6.4. Формулы качества прогноза и сравнения этапов

- [ ] Регрессия $Q,P,V,E$: считать MAE, RMSE и $R^2$; MAE использовать как основную метрику выбора модели, а predictive spread пяти seed показывать как оценку нестабильности.
- [ ] Зафиксировать основную метрику выбора модели: minimum MAE для $Q,P,V,cost,time$; minimum Brier score для вероятностей $R12,A$; maximum NDCG@10 для ranking. Дополнительно отчёт всегда содержит RMSE, $R^2$, ROC-AUC, PR-AUC, calibration error и coverage там, где метрика применима.
- [ ] Бинарные результаты $R,A$: ROC-AUC и PR-AUC, log loss/Brier score и калибровка; при дисбалансе не сообщать accuracy в одиночку.
- [ ] Сравнивать этапы на одном и том же test cohort и одном целевом исходе. Для этапа $k$ использовать только $X_{\le k}$: $\hat Q_k=f_k(X_{\le k})$. Сравнивать разность метрик с bootstrap-интервалами и одинаковым split.
- [ ] Измерять добавочную ценность этапа через разность MAE $\Delta_k=MAE_{k-1}-MAE_k$; положительное значение означает уменьшение ошибки после нового этапа. Отдельно сравнивать PR-AUC, RMSE, калибровку и долю заявок с достаточными данными.
- [ ] На синтетической когорте всегда считать C-index и time-dependent Brier для удержания; на source dataset рассчитывать их при наличии не менее 100 событий ухода и 100 цензурированных наблюдений, иначе явно выводить «недостаточно наблюдений» вместе с counts.

### 6.5. Метрики стоимости, сроков и расчетного эффекта

Для $N_h$ состоявшихся наймов и $N_v$ закрытых вакансий:

\[
C_{hire}=\frac{\sum_{i=1}^{N_h}C_i}{N_h},\qquad
T_{fill,i}=date_{close,i}-date_{open,i},\qquad
T_{fill}=\operatorname{median}_i(T_{fill,i}).
\]

Сравнение базового и модельного сценария:

\[
\Delta_C=C_{base}-C_{model},\quad
\Delta_T=T_{base}-T_{model},\quad
\Delta_Q=Q_{model}-Q_{base},\quad
Saving=N_h\Delta_C,\quad
ROI=\frac{Saving-C_{system}}{C_{system}}\times100\%.
\]

- [ ] Рассчитывать `C_hire` и `T_fill` на выбранном интервале; показывать отдельно mean, median, p25/p75, число вакансий и процент записей с полными данными.
- [ ] Считать `date_open` днём запуска поиска, `date_close` днём принятия принятого предложения/фактического выхода по фиксированной конфигурации `metric_definitions.yml`; `time_to_hire` считать от первого контакта до принятия предложения.
- [ ] Показывать абсолютные $\Delta_C,\Delta_T,\Delta_Q$, относительные изменения и `ROI`; стоимость разработки/эксплуатации хранить отдельными позициями. При $C_{system}=0$ показывать ROI как «не рассчитывается: отсутствуют системные затраты», а не делить на ноль.
- [ ] В приложении маркировать такую оценку как ретроспективное или сценарное сравнение; не называть её причинным эффектом ML без рандомизированного/квазиэкспериментального дизайна.

**Критерий контрольной точки:** каждое поле, формула, временное окно, baseline, целевой вес и метрика определены; прогон воспроизводится; отчёт показывает неопределённость и ограничения.

**Коммит:** `feat: implement match quality and hiring efficiency targets`

## 15. Определение готового PRISM-AI

Продукт считается завершённым, когда одновременно выполнены все условия:

- [ ] Вакансии, кандидаты и заявки ведутся отдельно и корректно связаны; история этапов сохраняется.
- [ ] Резюме импортируются, парсятся, проверяются человеком, защищённо хранятся и удаляются по выбранным правилам.
- [ ] Пользователь видит раздельные критерии соответствия, прогнозы результатов найма, неопределённость, факторы прогноза и происхождение данных.
- [ ] Приложение работает как самостоятельная recruiting CRM/ATS: база вакансий и кандидатов, заявки, этапы, история контактов, задачи рекрутера, локальная аналитика и резервные копии.
- [ ] Раздел «Графики» содержит агрегаты по всем вакансиям и кандидатам; карточка вакансии имеет собственные графики воронки и совпадений, а каждая заявка показывает свои графики соответствия резюме конкретной вакансии.
- [ ] В `reports/` сохранены профили и графики каждого открытого источника, каждого выпуска синтетических данных и каждого model run; `reports/index.md` позволяет открыть их для последующей технической документации.
- [ ] Сквозной синтетический датасет воспроизводим и приближен к профилям открытых источников; обучение, validation и test разделены без утечек, результаты сопровождаются конфигурацией и метриками.
- [ ] Сравнение моделей и этапов не допускает утечки; целевые переменные и метрики имеют ясные окна и определения.
- [ ] Приложение содержит рабочие интерфейсы вакансий, кандидатов, аналитики, рынка и настроек, без необходимости запускать команды для повседневной работы.
- [ ] API hh.ru соблюдает текущую документацию и ограничения, не загружает закрытые данные кандидатов и безопасно обращается с токеном.
- [ ] Есть локальное хранилище, экспорт, удаление, резервное копирование и проверенное восстановление.
- [ ] Универсальный экспорт данных работает без внешней HRMS; подключение Horilla остаётся дополнительным односторонним экспортным адаптером.
- [ ] Локальная сборка macOS автономна, не требует dev-инструментов, не теряет пользовательские данные при обновлении и запускается на целевом Mac без процедуры Developer ID/notarization.
- [ ] Техническая документация, руководство пользователя, модельные карточки и release checklist соответствуют фактическому коду и данным.
